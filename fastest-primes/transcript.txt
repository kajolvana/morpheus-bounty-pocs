3. Micro-optimizations tried (internal hrtime probes, N=5000000):
   - Marking variants: index-space marking won; number-space with a shift
     per write was worse (14.7-21.5 ms vs ~14.4-15.7 ms).
   - Count variants: branch 13.5-15.1 ms, xor 7.7-8.5 ms, sub 9.3-9.5 ms,
     SWAR byte-sum 2.8-4.2 ms -> SWAR chosen.
   - Segmented sieve block sizes (sieve phase): B=4096 ~11.5-12.8 ms,
     B=8192 ~10.4-11.1 ms, B=16384 ~10.0-10.9 ms (best), B=32768 ~11.0-12.7 ms,
     B=65536 ~15.4-16.2 ms, B=131072 ~14.1-24.0 ms -> B=16384 chosen.
   - Haszero zero-byte formula ((x-0x01010101)&~x&0x80808080) DISCARDED:
     verified wrong in Node (0x01000000 gives a false positive).
   Result after segmentation: N=5000000 best 90.6 ms, median 96.0 ms
   (N=1000000 best 81.9 median 86.5; N=100000 best 82.1 median 89.0).
   Node startup floor measured separately: `node -e ''` best 77.8 ms,
   median 83.0 ms — startup dominates every entry; compute is the margin.

4. Lehmer prime counting tried (lehmer.js, MAXV=100000 table + phi with
   memo + periodic table for s<=6, period 30030):
   - pi(5000000) itself takes only 0.56-0.74 ms.
   - Verified against segmented-sieve ground truth on 82,390 values
     (all N 1..20000, every 97th N to 5,000,000, near squares/cubes/fourth
     powers +/-2, known checkpoints): 0 mismatches.
   - BUT end-to-end it was NOT faster (N=5000000 best 85.6 ms, median
     95.8 ms) because module-load setup costs 8-13 ms (sieve to 1e5,
     piSmall/primes loop, smallPhi table).

5. BUG FOUND AND FIXED (phi shortcut): the periodic table in phi() was
   used for any s <= 6, but it is only valid for s == 6 (coprime to
   2,3,5,7,11,13). For s < 6 it returned phi(x,6) instead of phi(x,s).
   With MAXV=10000 this gave pi(5000000)=369595 instead of 348513
   (error exactly 368 = phi(10000,4) - phi(10000,6)); the bug was invisible
   at MAXV=100000 because phi is never called with s < 6 there.
   Fix: use the table only when s == 6; recurse for s < 6.
   Re-verified after the fix: diagnostic over n in [10000, 100000) went
   from 18,561 mismatches to 0; full 82,390-value sweep: 0 mismatches.
   Same fix applied to lehmer.js.

6. Crossover measured cold (fresh process per run, hrtime compute only):

What was tried and discarded
-----------------------------
- Non-segmented sieve (slower than segmented B=16384).
- Pure Lehmer with MAXV=100000 (setup 8-13 ms too big) and MAXV=50000
  (no better than MAXV=10000, noisier median).
- Haszero zero-byte counting formula (wrong, false positives).
- Branch / xor / sub count loops (all slower than SWAR byte-sum).
- Number-space marking with a shift per write (slower than index-space).
- Larger segment blocks B=32768/65536/131072 (all slower than B=16384).
